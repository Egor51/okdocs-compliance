# Методология RU premium report v2

Статус: implementation baseline. Документ фиксирует семантику отчёта и переход публичного API.

## Назначение и границы

RU premium report — автоматизированная оценка внешнего контура сайта по наблюдаемым техническим
и документарным признакам. Он не подтверждает полное соответствие 152-ФЗ: сканер не видит локальные
акты, договоры-поручения, реальные базы данных, процессы обработки вне сайта и действия сотрудников.

Отчёт обязан явно разделять:

1. **Observation** — воспроизводимый технический факт (запрос, cookie, header, форма, текст документа).
2. **Assessment** — оценку риска с учётом доступного юридического контекста.
3. **Coverage** — область, которую удалось или не удалось проверить.
4. **Sanction scenario** — справочную санкцию, применимость которой требует юридической квалификации.

## Статусы

До введения отдельных v2-enum действующие `VerificationStatus` трактуются так:

| Статус | Семантика v2 | Влияние на risk score | Влияние на coverage |
|---|---|---:|---:|
| `CONFIRMED` | Наблюдение воспроизводимо и доступный контекст подтверждает риск | 100% | нет |
| `DETECTED` | Наблюдение воспроизводимо, юридический контекст неполон | 65% | нет |
| `UNVERIFIED` | Проверка не завершена или факт основан только на предположении | 0% | уменьшает |
| `FALSE_POSITIVE` | Риск опровергнут | 0% | нет |

`UNVERIFIED` не является нарушением, не входит в severity-сводку подтверждённых рисков и не может
порождать штраф. До появления отдельного `coverageScore` неполнота отражается в diagnostics/quality.

## Score

Поле `score` в текущем API является индексом наблюдаемого риска, а не процентом соответствия
152-ФЗ. Оно рассчитывается только по `CONFIRMED` и `DETECTED`. Технические категории могут иметь
category cap. Ошибки сбора данных не уменьшают score и показываются отдельно.

В следующей версии контракта должны быть отдельные `riskScore`, `coverageScore` и
`technicalSecurityScore`; старое `score` сохраняется на переходный период.

## Штрафы

Свободный текст `fineAmount` нельзя парсить или суммировать. В частности, номера статей, суммы для
разных типов субъектов и санкции за повторность не образуют общий диапазон.

До введения структурированного `SanctionScenarioDto`:

- `summary.totalPotentialFine` всегда `null`;
- `fineAmount` в finding остаётся справочным текстом для обратной совместимости;
- для `UNVERIFIED` `fineAmount` не выдаётся клиенту;
- UI не должен показывать арифметическую сумму sanctions.

Целевая модель санкции содержит закон, статью/часть, тип субъекта, первое/повторное нарушение,
минимум/максимум, дату вступления нормы в силу и условие применимости.

## Cookies и внешние сервисы в RU

Отсутствие cookie-баннера само по себе не доказывает нарушение 152-ФЗ. Правило сначала фиксирует
storage/network observation, затем определяет назначение (`NECESSARY`, `SECURITY`, `ANALYTICS`,
`ADVERTISING`, `UNKNOWN`), наличие идентификатора, получателя, цель и заявленное основание.

Высокий риск допустим, когда, например:

- сайт заявляет согласие как основание, но аналитика запускается до выбора;
- необязательная обработка продолжается после явно выбранного отказа;
- подтверждённый сторонний получатель и фактическая обработка не раскрыты в политике;
- обнаружена обработка для прямого маркетинга, а предварительное согласие не подтверждено.

Неизвестное назначение cookie или недоступный consent-сценарий дают `UNVERIFIED`, а не нарушение.

## Evidence

Premium finding должен сохранять все затронутые страницы и, когда источник доступен: URL, время,
consent state, request URL/status/initiator, cookie name/domain/flags, тип источника, confidence и
matched signals. Значения cookie в отчёте не сохраняются — только безопасное имя и при необходимости
hash.

## Совместимость

- Исторические JSON-снапшоты не перерендериваются.
- Новые nullable-поля читаются старыми снапшотами как `null`/empty.
- Переход на report v2 выполняется через additive contract и feature flag.
- Изменение юридической семантики закрепляется regression/golden tests.
